# 08: 整数変換の codegen

種別: perf / 実装量: 中 / 設計判断: 中 (簡単な対処が効かないことは確認済み)

## 現象

`Repr::from_num` は LUT で桁を作り、`Repr::new_with` の `init` クロージャからスタック上の
16 バイトのバッファに直接書く。桁を作る部分は速く、u32 / i64 では `String` より速い。

| | LeanString | CompactString | std |
| --- | --- | --- | --- |
| `u32` | **11.374 ns** | 15.447 ns | 14.839 ns |
| `i64` | **11.959 ns** | 15.575 ns | 21.308 ns |
| `u64::MAX` | 27.221 ns | **17.202 ns** | 26.989 ns |
| `f64` | 25.189 ns | 24.923 ns | 112.64 ns |

`u64::MAX` だけ大きく負けているのは、20 桁が 16 バイトに収まらず必ず heap に確保するため。
24 バイト表現の CompactString なら inline に収まる。表現の大きさによる差なので、実装では埋められない。

asm を見ると、別に 2 つの問題がある
([research/codegen-baseline.md](../research/codegen-baseline.md) の §8)。

### 1. 戻り値の 16 バイトが 5 回のストアに分かれる

`u32` では `into_repr` が完全に展開され、heap の分岐も消えている (10 桁は必ず inline に収まることを
LLVM が桁数の計算から導いている)。ただ最後に `Repr` を書き出すところが 5 回のストアに分かれる。

```asm
	movq	-16(%rsp), %rcx
	movq	%rcx, (%rax)
	movl	-8(%rsp), %ecx
	movl	%ecx, 8(%rax)
	movzwl	-4(%rsp), %ecx
	movw	%cx, 12(%rax)
	movzbl	-2(%rsp), %ecx
	movb	%cl, 14(%rax)
	movzbl	-1(%rsp), %ecx
	movb	%cl, 15(%rax)
```

`LeanString::from(&str)` の inline 経路は同じ `Repr` を `movq` 2 本で書けている (§1)。
違いは値の出どころで、`from_str` は 2 つの u64 をレジスタで計算しているのに対し、
`new_with` はバイト単位で書いたバッファから値を読むので、LLVM が `Repr` のフィールドの境界で分けたまま
まとめ直せていない。桁を 2 バイトずつ書いた直後にワード単位で読むので、x86 では
store-to-load forwarding も効かない。

### 2. 符号付き整数では `into_repr` が展開されない

`i32` / `i64` では `into_repr` が呼び出し側に展開されず、`callq` になる。本体は `i32` で 138 命令、
`i64` で 314 命令ある。`u32` (96 命令の中に展開) と `u64` (217 命令の中に展開) は展開される。

`impl_NumToRepr_for_integers` が作る `into_repr` には、他の型 (f32/f64/u128/i128/NonZero) と違って
`#[inline]` が付いていない。ただ、付けても asm は変わらなかった。`M: Mutability` で generic なので
もともと MIR は下流に出ており、原因は大きさがインライン化の閾値を超えていることにある。

## 試して効かなかった対処

### `new_with` の中でワード単位に読み直す

`InlineBuffer::empty()` に書いた後、`ptr::read` で `[usize; 2]` として読み直してから
`Repr::from_inline` に渡す方法。生成された asm は完全に同じだった。LLVM は挟んだ `ptr::read` を
見通して、元のバイト単位の分割に戻してしまう。原因は読み方ではなく、`Repr` のフィールドの分け方にある。

### `new_with` の inline 分岐で `InlineBuffer::new` を使う

スタック上の `[u8; 16]` に書いた後、先頭 `len` バイトを `&str` として `InlineBuffer::new` に渡す方法。
`InlineBuffer::new` は 2 ワードをレジスタで組み立てるので、理屈では 2 ストアで済むはず。

実際は全体として悪くなった。`InlineBuffer::new` の長さによる分岐が加わって `into_repr` が大きくなり、
`u32` でも下流でインライン展開されなくなる (`probe_from_num` が 22 命令 + `callq into_repr`、
`into_repr` の本体は 117 命令)。桁を作る処理と長さの分岐を両方抱えた関数は、
インライン化の閾値に収まらない。

### `into_repr` に `#[inline]` を付ける

上の 2 のとおり、変化なし。

### 符号付きの絶対値の範囲を明示する

64-bit では `i32` も `u64` に広げてから桁を作っているので、LLVM が値の範囲 (2^31 以下) を
見失っているのではと考え、絶対値を計算した後に型の幅でマスクしてみた。asm は変わらなかった。
`i32` が展開されないのは、符号の処理が加わった分だけ大きいからだと考えられる。

### 型ごとに heap の分岐を `assert_unchecked` で消す

u8〜u32 / i8〜i32 は符号込みで最大 11 文字なので必ず inline に収まる。型ごとの桁数の上限を
`hint::assert_unchecked(len <= MAX_INLINE_SIZE)` で伝えれば heap の分岐が消える、という案。
しかし `u32` ではすでに消えており、`i32` の `into_repr` にも確保の呼び出しは無かった。
LLVM が自分で導けているので、やる意味は無い。

## 残っている案

### 案A: 桁を直接 2 つのワードに組み立てる

`new_with` を使わず、LUT から 2 バイトずつ書いていた部分を、レジスタ上でのシフトと OR に置き換える。
1 の原因を取り除ける唯一の方法。

- 対象は桁数が 16 以下に収まる型 (u8〜u32 / i8〜i32 と対応する `NonZero`) に限る。
  u64 / i64 / usize / isize (64-bit) は 20 桁になりうるので、今の経路を残す。
- 桁は下の位から作るので、レジスタ上では「書き込む位置に合わせてシフトして OR」になる。
  今のループが `curr` を減らしながら書いているのと同じ順番で書ける。
- `InlineBuffer::from_char` と同じく、各ワードを `to_le()` してから `transmute` すれば
  エンディアンに依存しない。

実装量は中くらい。2 (符号付きで展開されない) にも効く可能性がある。バッファへのストアと読み直しが
無くなる分 `into_repr` が小さくなるので、`i32` が閾値に収まるかもしれない。これは作ってみないと分からない。
逆に、上で試した `InlineBuffer::new` 経由の案のように関数が大きくなって `u32` まで展開されなくなる
おそれもあるので、`u32` と `i32` の両方で必ず確認する。

### 案B: 何もしない

`u32` / `i64` はすでに `String` より速く、`u64::MAX` の差は表現の大きさによるもの。
分割されたストアは数命令で、`Numbers` ベンチで差が出ないこともありうる。
案A を試して効果が誤差程度なら、そこで終わりにして記録を残す。

## 検証

- asm: `probe_from_num` の最後が `movq` 2 本になること。`probe_from_i32` から
  `callq into_repr` が消えるかも見る。`into_repr` が下流で展開されたままかは毎回確認する。ここがいちばん壊れやすい。
- criterion: `comparison.rs` の `Numbers` (u32 / i64 / u64::MAX / f64)。
  `u64::MAX` は変わらないはずなので、悪くなっていないことの確認に使う。
- テスト: `tests/property.rs` で、8/16-bit の整数は全数、それより大きい型は proptest で
  `to_string()` との一致を確かめている。proptest では 32-bit 以上の桁が上がる境目 (`9` → `10`、
  `99999999` → `100000000` など) や `MIN` / `MAX` を踏むとは限らないので、これらを列挙したテストを足す。
- Miri: 4 ターゲット。
