# 07: 共有バッファ比較の扱いを決める

種別: 方針決定 + doc / 小 API / 実装量: 小 / 設計判断: 中

調査は [research/equality.md](../research/equality.md) にまとめてある。ここでは選択肢と推奨だけを書く。

## 論点

`LeanString` / `LeanStr` の clone はバッファを共有するので、
「同じバッファの同じ範囲を指す 2 つのハンドル」の比較は内容を見ずに決まる。
これを既定の `==` / `Ord` に組み込むかどうか。

判断材料 (詳細は research 側):

- 現状の比較の codegen に無駄はない。近道を入れる以外に速くする手段は無い。
- 近道が効くのは heap / static を共有している場合だけ。16 バイト以下は inline なので、
  短い文字列のワークロードには一切効かない (inline 表現ではデータポインタが
  そのオブジェクト自身のアドレスになり、別インスタンス同士で一致しない)。
- 既定の `==` に入れると、最速の不一致ケースに 1 比較ぶんのコストが乗る。
  `char_str` の計測ではその劣化は 0.1〜0.2 ns 程度。
- 共有ハンドル同士の比較が支配的なワークロードでは、長い文字列で効果が大きい
  (`char_str` の計測で 4 KiB のとき約 -99%)。
- 呼び出し側が自分で近道を書くには「ポインタと長さが一致すれば内容も一致する」という
  保証が要るが、これはどこにも文書化されていない。

## 選択肢

### O1: ドキュメントのみ

`PartialEq` / `Ord` の doc、または crate レベルの CoW の説明に:

1. 比較は常に内容比較であること (実行時間の予測可能性を明文化する)
2. clone 同士の比較を速くしたい場合に、利用側が newtype で近道を書く方法

- 利点: コード変更ゼロ。方針が明快。
- 欠点: 近道のレシピが `as_ptr()` ベースの内部表現依存に見え、保証として弱い。

### O2 (推奨): `ptr_eq` を生やす + ドキュメント

`Arc::ptr_eq` / `Rc::ptr_eq` に相当する小さな pub API を足す。

```rust
impl LeanString {
    /// 2 つの文字列が同じバッファの同じ範囲を指しているなら `true`。
    ///
    /// `true` なら内容は必ず等しい。`false` でも内容が等しいことはある。
    /// clone 同士や、同じ `&'static str` から作った文字列同士で `true` になる。
    /// インライン化されている文字列 (`2 * size_of::<usize>()` バイト以下) では、
    /// 同じオブジェクトを 2 回借りた場合を除いて常に `false` になる。
    ///
    /// 比較の実行時間を予測可能に保つため `==` はこの判定を行わない。
    /// 共有された文字列の比較が支配的なワークロードでは、
    /// `a.ptr_eq(&b) || a == b` のように利用側で前置できる。
    pub fn ptr_eq(&self, other: &Self) -> bool {
        core::ptr::eq(self.as_ptr(), other.as_ptr()) && self.len() == other.len()
    }
}
```

- 既定の `==` は内容比較のままなので、実行時間の予測可能性は保たれる。
- 利用側は明示的に近道を書ける。`ecow` も同じ判断で `EcoVec::ptr_eq` を
  pub にしている ([research/equality.md](../research/equality.md) の §4 参照)。
- `Rc::ptr_eq` と違って長さも見る点は doc に明記する。`truncate` などで
  「同じポインタ・異なる長さ」のハンドルが作れるため。
- `LeanStr` にも同じものを生やすか: `LeanStr` は不変で共有が本旨なので、
  むしろこちらのほうが使われる。両方に生やすのが一貫する。
  相互比較 (`LeanString` vs `LeanStr`) 版は `as_ptr()` と `len()` を突き合わせるだけなので
  利用側で書ける。まずは同型同士だけでよい。

決めるべきこと:

- 命名。`ptr_eq` (`Arc`/`Rc`/`ecow` 踏襲) が第一候補。
- 「ポインタと長さが一致すれば内容も一致する」を pub な保証として書くかどうか。
  書くなら、将来 `as_ptr()` (`Deref<Target = str>` 経由) の返す値を変えられなくなる点を
  了解しておく。実際にはバッファ種別ごとに次のとおり成立している:
  - inline: ポインタは `self` のアドレスなので、別インスタンス同士では一致しない。
    誤って `true` になることはない。
  - heap (growable / exact): 共有ハンドルは同じポインタ。unshare や realloc で変わる。
  - static: 同じ `&'static str` から作れば同じポインタ。リンカのマージにより
    「別のリテラルが同じポインタ」になることはありうるが、その場合も内容は等しい。

### O3: `PartialEq` / `Ord` に組み込む

`Repr` に `content_eq` / `content_cmp` を足し、`PartialEq` 20 impl のうち同型同士と
相互比較、`Ord` 2 impl を差し替える (`char_str` と同じ形)。

不採用を推す。再考する条件を記録しておく:

- 共有バッファの比較が支配的なワークロードの利用報告があった場合
- 非共有ケースの劣化を消す実装 (バッファ種別で近道の適用を絞る、
  分岐配置を工夫する等) を asm で示せた場合

その際は [research/equality.md](../research/equality.md) の §4 に引用した
`char_str` の `content_eq` / `content_cmp` がそのまま設計図になる。
`content_cmp` の「ポインタ一致だが長さが違う ⇒ 接頭辞関係なので長さが順序を決める」は
間違えやすいので、採用するならその部分は必ず写す。

## 成果物 (O2 を採る場合)

- `LeanString::ptr_eq` / `LeanStr::ptr_eq` の実装 (数十行)
- doc:
  - `ptr_eq` の保証と、inline では基本的に `false` になること
  - `PartialEq` / `Ord` が常に内容比較であることの明文化
  - `a.ptr_eq(&b) || a == b` のレシピを doctest として書く
    (共有 clone で `true`、内容が同じ別確保で `false` になるケース)
- CHANGELOG に新 API として記載

## 検証方針

近道を trait に入れない以上、性能検証は「`ptr_eq` が 2 比較にコンパイルされる」ことを
asm で確認するだけで足りる。doctest がそのまま挙動のテストになる。

## 依存

なし。いつでも実施できる。
